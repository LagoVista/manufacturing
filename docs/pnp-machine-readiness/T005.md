# T005 — Auto feeder control panel

**Status:** Accepted / closed — November 27, 2026. Operator confirmed discovery, identify, initialize, advance/retract and satisfactory console feedback on physical feeders. See [review and residual limits](T005-review.md).

**Workstream:** [Pick-and-place machine readiness](README.md)

## Goal

Expose practical operator controls and feedback for automatic feeders in the machine UI.

## Scope

Inspect existing automatic feeder contracts, transport and WPF controls. Reuse available commands for identification, status, feed/advance and other supported functions; display confirmed results, errors and connection state. Keep manual actions operator-triggered and prevent conflicting commands.

## November 27 implementation handoff

Start with the existing WPF AutoFeederControl and PhotonFeedersControl, AutoFeederViewModel, PhotonFeederViewModel, IPhotonFeederViewModel, AutoFeeder model and existing IPhotonProtocolHandler / RS485 transport. Do not introduce a second feeder stack. T006/T007 will build on the same controls and identity; leave optical calibration and job sequencing for those tasks.

- Present discovered versus configured feeders, slot, physical Photon address/ID, initialization/connection state, component and tape pitch where available. Explicitly distinguish missing, mismatched and unknown status. Use existing templates and machine rail configuration. Do not equate a database record with a responding feeder.
- Provide operator-triggered discovery, initialize, forward and reverse test feed using protocol-supported distances and units; show the intended slot/ID, distance, pending operation and confirmed outcome. No new firmware/protocol commands assumed. Validate pitch/distance and component-independent manual testing as supported by the existing hardware; do not silently use a guessed pitch. No automatic discovery movement or inventory changes. Preserve existing setup controls.
- Address observed reliability defects in PhotonFeederViewModel: InitializeFeederAsync increments rather than decrements its retry counter; advance and retract return success unconditionally, and the shared receive handler signals completion even for timeout/status errors. Ensure one bounded in-flight transaction per bus, subscribe/reset before dispatch, correlate expected packet/address/status, distinguish timeout/malformed/unrelated/negative response from success, clear handlers on all exit paths, and avoid stale replies satisfying a new command. Do not automatically resend a physical advance/retract after an ambiguous outcome; surface uncertain tape position for operator reconciliation. Audit existing initialization-on-connect behavior for ordering and bounded completion; do not add new automatic physical actions.
- Manual movement must not decrement inventory or trigger picks. Existing NextPartAsync decrements count before checking movement result; flag and protect failure semantics where this change intersects the shared path, without redesigning production job execution. Keep physical response acknowledgment distinct from proof that a part is present.
- Respect machine connection/idle, operator clearance and existing interlocks. Disable conflicting operations and wrong/missing feeder selection. No automatic axis motion or feeder advancement just by opening the panel. Confirm intended feeder and unloaded/safe test conditions before exercising hardware.
- Focused tests: request correlation, success/failure/timeout/stale response, bounded initialization, concurrent command rejection, invalid slot/ID/pitch, disconnect and cleanup, no inventory change in manual testing. Build the WPF application where supported and report exact test/build evidence. Supervised physical check: discover one actual feeder, confirm slot and ID, initialize, advance a known pitch, retract a supported amount, and verify actual tape motion and visible failure status. Do not claim hardware verification from a simulated reply.
